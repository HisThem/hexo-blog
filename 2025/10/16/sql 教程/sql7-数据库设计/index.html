‘数据库设计’是指 对于一个给定的应用环境，构造（设计）优化的数据库 逻辑模式 和物理结构 ，并 据此建立数据库及其应用系统，使之能够有效地存储和管理数据，满足各种用户的应用需求，包括信息管理要求和数据操作要求。

  • 信息管理要求：在数据库中应该存储和管理哪些数据对象。

  • 数据操作要求：对数据对象需要进行哪些操作，如查询、增、删、改、统计等操作。

数据库设计的目标是为用户和各种应用系统提供一个 信息基础设施 和高效率的运行环境。

  • 高效率的运行环境

    • 数据库数据的存取效率高
    • 数据库存储空间的利用率高
    • 数据库系统运行管理的效率高

7.1 数据库设计概述

7.1.1 数据库设计的特点

  • 数据库建设的基本规律：

    • “三分技术，七分管理，十二分基础数据” 这句话是业界经验的总结，强调了各个方面的重要性。
      • 管理 (Management):
        • 包括数据库建设项目的管理。
        • 也包括企业（即应用部门）自身的业务流程管理。
      • 基础数据 (Basic Data):
        • 指的是数据的收集、整理、组织，并且要持续进行更新维护。

  • 结构（数据）设计和行为（处理）设计相结合：

    • 现代数据库设计强调将数据库的 结构设计 （关注数据如何组织）与 数据处理设计（关注数据如何操作和使用，即行为）紧密地结合起来。
    • 过去存在结构和行为分离设计的问题：
      • 传统软件工程：更侧重行为设计 (Heavy on Behavior Design):
        • 往往忽视了对应用中数据内在含义（语义）的分析和抽象。
        • 只要有可能，就尽量推迟数据结构设计的决策。
      • 早期数据库设计：更侧重结构设计 (Heavy on Structure Design):
        • 集中于研究数据模型和数据库建模方法。
        • 相对忽视了用户行为（即数据处理需求）对数据库结构设计应有的影响。

7.1.2 数据库设计方法

  • 大型数据库设计 (Large-Scale Database Design):

    • 是一项涉及多学科的综合性技术，可以看作一个庞大的工程项目。
    • 要求设计者具备多方面的知识和技术，主要包括：
      • 计算机的基础知识
      • 软件工程的原理和方法
      • 程序设计的方法和技巧
      • 数据库的基本知识
      • 数据库设计技术
      • 相关应用领域的知识

  • 数据库设计方法

    • 手工试凑法: (结合手工操作与个人经验)
      • 设计质量与设计人员的经验和水平有直接关系。
      • 缺乏科学理论和工程方法的支持，使得工程的质量难以保证。
      • 数据库运行一段时间后，常常会不同程度地发现各种问题，这增加了后续的维护代价。
    • 规范设计法: (基本思想：过程迭代和逐步求精)
      • 新奥尔良（New Orleans）方法
      • 基于 E-R 模型（实体 - 关系模型）的数据库设计方法
      • 基于 3NF（第三范式）的设计方法
      • 面向对象的数据库设计方法
      • 统一建模语言（UML）方法

7.1.3 数据库设计的基本步骤

数据库设计分 6 个阶段：

  • 需求分析

  • 概念结构设计

  • 逻辑结构设计

  • 物理结构设计

  • 数据库实施

  • 数据库运行和维护

需求分析和概念设计独立于任何数据库管理系统

逻辑设计和物理设计与选用的数据库管理系统密切相关

图例：数据库设计步骤

  1. 需求分析阶段

    • 是否充分与准确，决定了构建数据库的速度和质量

  2. 概念结构设计阶段

    • 通过对用户需求进行综合、归纳与抽象，形成一个独立于具体数据库管理系统的概念模型

  3. 逻辑结构设计阶段

    • 将概念结构转换为某个数据库管理系统所支持的数据模型，并对其进行优化

  4. 物理结构设计阶段

    • 为逻辑数据结构选取一个最适合应用环境的物理结构，包括存储结构和存取方法

  5. 数据库实施阶段

    • 根据逻辑设计和物理设计的结果构建数据库
    • 编写与调试应用程序
    • 组织数据入库并进行试运行

  6. 数据库运行和维护阶段

    • 经过试运行后即可投入正式运行
    • 在运行过程中必须不断对其进行评估、调整与修改

设计一个完善的数据库应用系统 往往是上述 6 个阶段的不断反复；

这个设计步骤既是数据库设计的过程，也包括了数据库应用系统的设计过程；

把数据库的设计和对数据库中数据处理的设计紧密结合起来，将这两个方面的需求分析、抽象、设计、实现在各个阶段同时进行，相互参照，相互补充，以完善两方面的设计。

我们主要学习在 逻辑设计阶段 的内容。

7.2 需求分析

7.2.1 需求分析的任务

  • 数据库设计定义:

    • 针对特定应用环境，构造优化的数据库逻辑模式和物理结构。
    • 建立数据库及其应用系统，以有效存储和管理数据。
    • 满足用户信息管理要求（存储哪些数据对象）和数据操作要求（如何操作数据）。

  • 数据库设计的目标:

    • 为用户和应用系统提供信息基础设施。
    • 创造高效率的运行环境，包括：
      • 数据存取效率高。
      • 存储空间利用率高。
      • 系统运行管理效率高。

  • 7.1.1 数据库设计的特点:

    • 基本规律: " 三分技术，七分管理，十二分基础数据 "。强调管理和基础数据（收集、整理、组织、更新）的重要性。
    • 结构（数据）设计和行为（处理）设计相结合:
      • 需将数据库结构设计与数据处理设计紧密结合。
      • 传统软件工程偏重行为设计，早期数据库设计偏重结构设计，现代观点是两者结合。

  • 7.1.2 数据库设计方法:

    • 知识要求: 计算机基础、软件工程原理、编程技巧、数据库知识、数据库设计技术、应用领域知识。
    • 手工试凑法:
      • 质量依赖设计者经验。
      • 缺乏科学理论和工程方法支持，质量难保证。
      • 易导致后期问题，增加维护代价。
    • 规范设计法 (基本思想：过程迭代和逐步求精):
      • 新奥尔良（New Orleans）方法
      • 基于 E-R 模型的设计方法
      • 基于 3NF（第三范式）的设计方法
      • 面向对象的数据库设计方法
      • 统一建模语言（UML）方法

  • 7.1.3 数据库设计的基本步骤 (6 个阶段):

    1. 需求分析: 核心是准确收集用户在数据和处理上的需求，形成需求说明书。独立于 DBMS。
    2. 概念结构设计: 将需求抽象为独立于 DBMS 的概念模型（如 E-R 图）。
    3. 逻辑结构设计: 将概念模型转换为特定 DBMS 支持的数据模型（如关系模型），并优化。与 DBMS 相关。
    4. 物理结构设计: 为逻辑模型选择合适的物理结构（存储结构、存取方法）。与 DBMS 相关。
    5. 数据库实施: 建立数据库、编程调试、数据入库、试运行。
    6. 数据库运行和维护: 评价、调整、修改。
    • 这是一个迭代反复的过程，数据库设计与应用系统设计紧密结合。

  • 参与数据库设计的人员:

    • 系统分析人员、数据库设计人员 (全程, 决定质量)
    • 数据库管理员 (DBA)、用户代表 (需求分析, 运行维护)
    • 应用开发人员 (程序员、操作员) (实施阶段)

  • 7.1.4 数据库设计过程中的各级模式:

    • 需求分析阶段: 综合用户应用需求。
    • 概念设计阶段: 形成概念模式 (如 E-R 图)，独立于 DBMS。
    • 逻辑设计阶段: 形成数据库逻辑模式 (如关系模式) 和外模式 (视图)。
    • 物理设计阶段: 形成数据库内模式 (物理存储安排、索引)。

7.2 需求分析

定义: 分析用户要求，是设计的起点，准确性至关重要。

7.2.1 需求分析的任务

  • 调查现实世界处理对象。

  • 了解原系统工作概况。

  • 明确用户各种需求：

    • 信息要求: 需要什么信息，导出需要存储哪些数据。
    • 处理要求: 需要完成哪些处理功能，性能要求。
    • 安全性与完整性要求。

  • 确定新系统功能，并考虑未来扩展。

  • 确定需求的难点: 用户不熟悉计算机，设计人员不熟悉业务。

  • 解决方法: 设计人员与用户深入交流。

7.2.2 需求分析的方法

  • 调查用户需求的步骤:

    1. 调查组织机构情况、各部门职责。
    2. 调查各部门业务活动（输入、加工、输出数据）。
    3. 协助用户明确新系统要求。
    4. 确定新系统边界（哪些功能由计算机完成，哪些由人工完成）。

  • 常用调查方法: 跟班作业、开调查会、请专人介绍、询问、设计调查表、查阅记录。

  • 分析与表达: 常用结构化分析方法 (SA 方法，自顶向下、逐层分解)。需求分析报告需用户认可。

7.2.3 数据字典

  • 数据字典是关于数据库中数据的描述，即 元数据，不是数据本身。

  • 数据字典在需求分析阶段建立，并不断完善。

  • 数据字典是进行详细的数据收集和数据分析所获得的主要结果。

  • 数据字典的内容:（了解即可）

    • 数据项: 最小数据单位。描述 ={名称, 含义, 别名, 类型, 长度, 取值范围, 取值含义, 与其他数据项关系, 数据项间联系}。
    • 数据结构: 数据间的组合关系。描述 ={名称, 含义, 组成 (数据项 / 数据结构)}。
    • 数据流: 数据结构在系统内传输路径。描述 ={名称, 说明, 来源, 去向, 组成, 平均 / 高峰期流量}。
    • 数据存储: 数据结构停留或保存处。描述 ={名称, 说明, 编号, 输入 / 输出数据流, 组成, 数据量, 存取频度 / 方式}。
    • 处理过程: 用判定表 / 树描述具体逻辑。数据字典描述 ={处理过程名, 说明, 输入 / 输出数据流, 处理简要说明 (功能, 处理要求如频度 / 响应时间)}。

7.3 概念结构设计

课程讲义 PDF 未随本文转载。

将需求分析得到的用户需求抽象为信息结构（即概念模型）的过程就是概念结构设计。

7.3.1 概念模型的特点

  • 真实充分反映现实世界。

  • 易于理解 (方便与用户交流)。

  • 易于更改和扩充。

  • 易于向各种数据模型转换。

  • 常用工具: E-R 模型。

7.3.2 E-R 模型 (实体 - 关系模型)

  • 回顾基本概念：

    • 实体 (Entity):
      • 客观存在并可相互区别的事物称为实体。可以是具体的人、事、物或抽象的概念。
      • 每一个实体有一个“实体名”，同类实体具有相同的实体名。
    • 属性 (Attribute):
      • 实体具有的某一特性。每一个属性有一个‘属性名’，在同一个实体内属性名互不相同。
    • 码 (Key):
      • 唯一标识实体的属性集。
      • 在一个实体集中，可以通过‘码’的取值来区分不同的实体。
    • 实体型 (Entity Type):
      • 用实体名及其所有属性名的集合来抽象和刻画同类实体
      • 实体的实体名及其所有属性名的集合，称为该实体的‘实体型’
    • 实体值 (Entity Value):
      • 实体中的属性可以有值，一个实体的所有属性值的集合被称为该实体的‘实体值’。（也被称为‘实体实例’，Entity Instance）
    • 实体集 (Entity Set):
      • 同一实体型的实体集合。
      • 同一个实体集中的所有实体，具有相同的实体型但实体值互不相同。
    • 联系 (Relationship):
      • 现实世界中事物内部以及事物之间的联系，在信息世界中反映为实体（型）内部的联系和实体（型）之间的联系。
      • 每一个联系有一个‘联系名’

实体与联系

实体 & 实体名实体型 & 实体值实体集：一组具有相同实体型的实体的集合

  • 每一个实体集也有一个名字，实体的实体名，通常也被作为对应实体集的名字

实体型是模板，实体值是实例，实体集是一堆实例的集合。

联系的分类

  • 二元联系：两个实体型（实体集）间的联系

    • 一对一 (1:1)
    • 一对多 (1:n)
    • 多对多 (m:n)

  • 多元联系（两个以上实体型）也存在 1:1, 1:n, m:n。

    • 一门课程可以有若干个教师讲授、使用若干本参考书，而每一个教师只讲授一门课程，每一本参考书只供一门课程使用，则课程与教师、参考书之间是一对多的联系。
    • 一个供应商可以向多个项目供应多种零件，每个项目可以使用多个供应商供应的多种零件，每种零件可由不同供应商供给多个项目，供应商、项目、零件三者之间是多对多的联系。

  • 一元联系（单个实体型内）也存在 1:1, 1:n, m:n。

    • 例如，职工实体型内部具有领导与被领导的联系，即某一职工（干部）“领导”若干名职工，而一个职工仅被另外一个职工直接领导，因此这是一对多的联系。
      • 注：“领导”是关系名，一元联系中的实体只有职工

联系的度

联系的度：参与联系的实体型的数目

  • 2 个实体型之间的联系度为 2，也称为二元联系

  • 3 个实体型之间的联系度为 3，称为三元联系

  • N 个实体型之间的联系度为 N，也称为 N 元联系

参与到一个练习中的实体的个数，被称为联系的“度”

  • “领导”联系：一元联系，联系的度是 2

E-R 图

  • E-R 图表示法:

    • 实体型: 矩形。
    • 属性: 椭圆形 (用无向边连接到实体型)。
      • 用下划线表示主属姓名
    • 联系: 菱形 (用无向边连接各有关实体型，同时在无向边旁标上联系的类型)。联系也可有属性。

在阅读 E-R 模型时，只有同时关注 实体 A、实体 B、实体 A 与 B 之间的联系 三个值才有意义，仅关注一个实体和一个关系是没有意义的。（如仅关注上图中的“供应商”和“供应”是揣摩不出含义的）

7.3.3 扩展的 E-R 模型

ISA 联系

有的实体型是某个实体型的子类型，这种父类 - 子类联系称为 ISA 联系，表示“is a”语义。用△表示。

ISA 联系的性质

  • 子类继承了父类的所有属性

  • 子类也可以有自己的属性。

分类属性

分类属性是父实体型的一个属性；根据分类属性的值把父实体型中的实体分派到子实体型中

不相交约束与可重叠约束

  • 不相交约束 (X)

    • 父实体不能同时属于多个子类，最多只能属于一个子类实体集。
    • 用 ISA 联系符号三角形的一个叉号“X" 来表示。

  • 可重叠约束:

    • 父实体可同时属于多个子类。
    • 子类符号中没有叉号表示是可重叠的。
完备性约束

  • 完全特化 (双线): 父实体必须是某个子类实体。

  • 部分特化 (单线): 父实体不必是子类实体。

  • 完全特化用父类到子类的双线连接来表示

  • 部分特化用父类到子类的单线连接来表示

基数约束

基数约束表示一个 实体在联系中出现的最少和最多次数，常用 min..max 形式表示，要求满足 0 ≤ min ≤ max。

常见写法示例：

  • 0..1：可选参与，最多一次

  • 1..1：强制参与，且仅一次

  • 0..*：可选参与，可多次

  • 1..*：强制参与，可多次其中 * 表示无上限（无限次）

这是书上的例子。但是用数值 3、20、30 等来表示基数约束中确定的最少或最多次数并不常见，数字的位置也不正确（写反了）。接下来我们将给出常用的规范表示.

基数约束的意义
1. 参与约束（Participation Constraint）

根据 最小值 min 的取值，分为：

最小值（min） 类型 含义
0 非强制参与 实体可参与联系，也可不参与（Optional）
1 强制参与 每个实体必须至少参与一次该联系（Mandatory）
2. 参与次数（Participation Count）

根据 最大值 max 的取值，分为：

最大值（max） 类型 含义
1 单值参与 每个实体在联系中最多出现一次（Single）
* 多值参与 每个实体可以多次出现在联系中（Multiple）
基数约束的表示

实体 E 在联系 R 中的基数约束可被表示为 card(E, R)，可以用一个数对 min..max 来表示。

基数约束示例
函数关系与基数约束

以二元联系为例，可以根据实体型在联系中的‘最大参与基数 max’的取值来确定联系上的‘函数关系’。

联系上的‘基数约束’ 包含‘函数关系’ 约束，并具有比函数关系更多的语义信息。

一对一、多对多、一对多的基数约束实例：

可以通过基数约束来描述原本语义不太好描述的“函数关系”。

Part-of 联系

  • Part-of 联系: 描述一个实体型是另一个实体型的一部分。

    • 非独占联系: 整体破坏，部分仍可存在 (用 非强制参与 联系表示)。
    • 独占联系: 整体破坏，部分不能存在 (用 弱实体 类型和 识别联系 表示)。
弱实体型和识别联系

  • 弱实体型: 其存在依赖于其他实体型的存在。用双矩形表示。

    • 否则成为强实体型
    • 此外，还使用指向识别联系的箭头来表示弱实体型

  • 识别联系: 标识弱实体的联系。用双菱形表示。

还款依赖与贷款，如果贷款不存在，则还款也没有意义。因此还款是弱实体型，识别联系即为还贷

属性的划分

  • 根据属性在区分不同实体中的作用来划分

    1. 标识符（Identifier）
      • 在关系数据库中，又被称为‘关键字’(key)、键、码、候选关键字(candidate key)、候选键、候选码
    2. 描述符（Descriptor）
      • 除标识符之外的其他属性都被称为描述符

  • 根据属性域的定义来划分
    3. 单值属性（single-valued attribute）
    - 属性只能取定义域内的一个值（可以是一个原子值，也可以是一个组合值）
    4. 组合属性（a composite attribute）
    - 由一组简单属性组成，用来共同描述一个属性
    5. 多值属性（a multi-valued attribute）
    - 对于一个实体实例，可以取多个值

在一个实体集中，可能存在 多个 identifier，只能从中选择一个作为 primary identifier 并用 下划线 在 ER 图中将其标识出来。

属性基数

属性的基数约束可以用 (x, y) 表示，其中：

  • x 表示 最小值 （属性值是否 必须存在）

  • y 表示 最大值 （属性值是否 可以有多个）

表达式 含义
(0, ?) x = 0 表示该属性 可以为空 ，即某个实体 可以没有该属性的值（可选属性）
(1, ?) x = 1 表示该属性 不允许为空 ，即 每个实体必须有该属性的值（必选属性）
(?, 1) y = 1 表示该属性是 单值属性 ，即每个实体 至多只能有一个该属性的值（如姓名）
(?, *) y = * 表示该属性是 多值属性 ，即每个实体 可以有多个该属性的值（如电话号码、邮箱

  • 每一个 student_name 必须包含一个 lname 和一个 fname，可以没有或者包含一个 midinitial。

E-R 模型的设计

E-R 模型的设计任务

  • 标识系统中的 实体 、属性 与 联系

  • E-R 图表示

E-R 模型的设计选择

对于现实世界中的某个概念，我们应该将它抽象为：

  • 实体 or 属性 ？

  • 实体 or 联系 ？

  • 二元联系 or 三（多）元联系 ？

  • 联系的函数关系 ？

    • 基于现实世界中的语义约束来定义

  • 属性的依附对象：实体 or 联系 ？

    • 实体 (集) 中的属性
      • 是该实体的内在特征，不会因为某些联系的出现而产生改变或消亡
    • 联系上的属性
      • 用于描述因联系的发生而需要记录、存储下来的信息
      • 其值会随着联系的产生而出现，也会随着联系的消亡而消亡
实体 or 属性？

  • 实体：需要进一步多方面的描述信息

  • 属性：单一的描述值（非结构化的单值信息）

现实世界中的某个概念, 究竟是被抽象为 ER 模型中的一个‘实体’，还是某个实体上的一个‘属性’，取决于其取值情况。

例如：学生的身份证号码

  • 如果用户只需要访问学生的身份证号码，那么可以将‘身份证号码’作为‘学生’实体的一个属性

  • 如果还需要访问身份证相关的其他信息，如签发机关、有效期限等，则必须将与身份证相关的身份证号码、签发机关、有效期限等信息聚合成一个‘身份证’实体，再通过‘学生’和‘身份证’之间的联系来建立人和身份证之间的拥有关系。

实体 or 联系？

  • 实体：可以独立存在的持久对象。这些对象可以是有形的（如人、物体等），也可以是无形或抽象的（如组织机构、地理位置等）

  • 联系 ：因为某种需要或某件事情的发生而产生的信息， 通常与现实世界中的多个对象有关

有些时候，现实世界中的某些事件 (Event) 也可以被抽象为模型中的
‘实体’概念，例如：商品销售

  1. 如果是实体店的商品零售，那么可以用商品、顾客、销售商等之间的二元或多元联系来表示

  2. 如果是大宗商品或者网络销售，买卖双方之间通常都会签订销售合同或订单(Order)，那么也可以将合同或订单抽象为‘实体’，再通过订单实体与顾客、商品、销售商等实体之间的若干个二元联系来建立买卖双方的供销关系。

二元联系 or 三（多）元联系 ？

  • 取决于一个联系的语义描述需要，以及因此而涉及到的实体的个数

  • 在三 (多) 元联系中，在下述情况下也可以考虑采用若干个二元联系来实现：“用户只需要使用它们之间的两两联系，且不会出现二义性（歧义性）”

  • 或者，直接将联系抽象为‘实体’，再在该‘联系实体’与其他实体之间建立若干个二元联系

7.3.4 概念结构设计方法与步骤

  • 设计方法:

    • 自顶向下: 先定义全局框架，再逐步细化。
    • 自底向上: 先定义各局部应用，再集成。
    • 逐步扩张: 从核心概念结构向外扩充。
    • 混合策略: 常用自顶向下需求分析，自底向上设计概念结构。

  • 实体与属性的划分原则:

    1. 属性必须是不可分的原子数据项，不能再有需要描述的性质。
    2. 属性不能与其他实体具有联系。
    • 能作为属性的尽量作为属性，以简化 E-R 图。

  • E-R 图的集成 (自底向上时):

    1. 合并 E-R 图，解决冲突:
      • 属性冲突: 属性域 (类型、范围、单位) 不同。
      • 命名冲突: 同名异义，异名同义 (实体、联系、属性名)。
      • 结构冲突: 同一对象抽象不同 (实体 vs 属性)，实体属性不完全相同，联系类型不同。
    2. 修改和重构初步 E-R 图，消除冗余:
      • 冗余数据: 可由基本数据导出。
      • 冗余联系: 可由其他联系导出。
      • 用分析方法或规范化理论辅助消除。注意：并非所有冗余都必须消除，有时为效率保留。

7.4 逻辑结构设计

  • 任务: 将前一阶段设计得到的概念数据模型 (EE-R 模型) 转换成用户所选择的数据库管理系统 (DBMS) 支持的逻辑数据模型。

    • 由于在概念设计阶段选择的是 EE-R 模型，而目前最流行的是关系数据库系统，因此，数据库的逻辑设计的基本任务就是：
      • 将 EE-R 模型转换成等价的关系数据库模式

  • 转换内容: E-R 图的实体、属性、联系 -> 关系模式；模型优化；设计用户子模式。

E-R 图向关系模型的转换原则

  • 实体型: 一个实体型转换为一个关系模式 (属性 -> 列, 码 -> 主码)。

    • 例：实体型 学生(学号, 姓名, 性别) → 关系模式 学生(学号, 姓名, 性别)，主码为 学号。

  • 1:1 联系:

    • 可转为一个独立关系模式 (属性含两端实体码 + 联系属性，两端码均为候选码)。
      • 例：学生(学号) 与 宿舍(宿舍号) 之间有 1:1 联系 入住(入住时间)，
        • 可建关系 入住(学号, 宿舍号, 入住时间)，学号 和 宿舍号 为候选码。
    • 或与任一端实体关系模式合并 (在其属性中加入另一端码 + 联系属性)。
      • 例：将 宿舍号 和 入住时间 加入 学生 → 学生(学号, 姓名, 性别, 宿舍号, 入住时间)。

  • 1:n 联系:

    • 可转为一个独立关系模式 (属性含两端实体码 + 联系属性，n 端实体码为新关系码)。例：教师(工号) 与 课程(课程号) 之间有 1:n 联系 教授(学期)，可建关系 教授(课程号, 工号, 学期)，主码为 课程号。

    • 或与 n 端实体关系模式合并 (在 n 端属性中加入 1 端码 + 联系属性，减少关系数)。例：将 工号 和 学期 加入 课程 → 课程(课程号, 名称, 学分, 工号, 学期)。

  • m:n 联系: 转换为一个独立关系模式 (属性含两端实体码 + 联系属性，两端实体码组合为新关系码)。

    • 例：学生(学号) 与 课程(课程号) 之间有 m:n 联系 选修(成绩)，
    • 建关系 选修(学号, 课程号, 成绩)，主码为 (学号, 课程号)。

  • 多元联系 (三个以上实体): 转换为一个关系模式 (属性含各实体码 + 联系属性，各实体码组合为新关系码)。

    • 例：学生(学号)、课程(课程号)、教师(工号) 三者的多元联系 考试(时间, 地点)，
    • 建关系 考试(学号, 课程号, 工号, 时间, 地点)，主码为 (学号, 课程号, 工号)。

  • 相同码的关系模式可合并: 减少关系个数。

    • 例：两个关系 学生基本信息(学号, 姓名, 性别) 与 学生联系方式(学号, 电话)，可合并为
    • 学生(学号, 姓名, 性别, 电话)。

逻辑结构设计的基本方法

  • 每个‘实体集’被转换成一个关系

    • 关系及其属性的命名采用原实体集及其属性的名称

  • 每个‘联系’通常也被转换成一个关系

    • 联系名 -> 关系名，该关系模式中的属性由两部分组成：
      • 联系自身所具有的属性
      • 与该联系相关的实体集的标识属性
    • 来自于相关实体集的标识属性也是相关实体集转换得到的关系模式的主码，因此它们也是联系转换得到的关系模式中的外码

    • 在同一个关系模式中，属性名具有唯一性属性域的定义

6．关系数据库管理系统（DBMS）

为满足数据库系统在性能、存储空间等方面的要求及其它限制条件所做的模式调整与修改。包括：

  1. 逆规范化

    • 将多个相关表合并为一个大表，减少 JOIN，提高系统性能

  2. 关系的分割

    • 调整每个关系的大小，提高在单个关系上的数据存取效率。
    • 常用分割方法：
      • 水平分割
        • 将一个关系的元组集合划分为若干个不相交的子集，每个子集对应一个子关系模式；
      • 垂直分割
        • 将一个关系模式纵向分解成若干个子关系模式。（不同于规范化设计中的模式分解）

  3. 尽量使用快照

    • 快照(snapshot)：create snapshot <snapshot-name> as <select-statement>;
      • 通过创建‘快照’，可以用一条 select 查询语句来为数据库中的某张表、或者为某个数据查询请求的执行结果创建一个不可修改的、持久化的数据备份。
      • 在执行 create snapshot 命令时，DBMS 将执行对应的查询语句<select-statement>，并将查询执行结果以‘表’的形式持久存储在数据库中。
      • 在实际应用中，应用程序可以通过访问快照直接使用保存在数据库中的查询结果，不必再去执行对应的查询命令，有效提高了应用访问效率。特别适合于业绩统计、库存盘点、实时计费等应用场景。
    • 快照的维护：DBMS 提供了两种快照结果的更新方式
      • 由 DBMS 周期性地自动刷新快照的结果数据
      • 由用户通过执行快照刷新命令来手工刷新快照的结果数据

8. 关系视图的设计

在关系模式基础上所设计的直接面向操作用户的视图，即用户的‘外模式’，它可以根据用户的需求随时定义或重新定义，一般 RDBMS 均通过‘视图’(view)来提供关系视图的功能。

关系视图的作用

  • 提供数据的逻辑独立性

  • 能满足不同用户的不同数据需求

  • 提供一定的数据安全、保密功能

  • 数据模型的优化 (以关系模型为例):

    • 规范化理论指导:
      • 写出各关系模式内部属性间数据依赖，进行规范化 (消除部分 / 传递函数依赖等)。
      • 写出不同关系模式间数据依赖，进行极小化处理，消除冗余联系。
    • 权衡: 并非规范化程度越高越好。高规范化可能增加连接操作，影响效率。若关系主要用于查询，某些更新异常可能不重要。需平衡响应时间和潜在问题。
    • 关系模式的分解: 提高操作效率和空间利用率。
      • 水平分解: 将元组集划分子集 (如常用数据分离)。
      • 垂直分解: 将属性集划分子集 (如常用属性分离)。需保证无损连接和保持函数依赖。

  • 设计用户子模式 (视图):

    • 使用更符合用户习惯的别名。
    • 针对不同用户定义不同视图，保证安全性。
    • 简化用户对系统的使用 (将复杂查询定义为视图)。

  • 数据库管理系统适应性转换:

    • 根据所选用 DBMS 的具体功能和限制，对一般数据模型进行调整。对关系模型通常简单。

7.5 物理结构设计

  • 定义: 为逻辑数据模型选取最适合应用要求的物理结构 (存储结构与存取方法)。依赖于选定的 DBMS。

  • 步骤:

    1. 确定数据库的物理结构 (主要指存取方法和存储结构)。
    2. 对物理结构进行评价 (时间、空间效率)。不满足则重设或修改。

  • 物理设计内容与方法:

    • 准备工作: 了解应用环境、事务分析 (查询 / 更新内容、频率、性能要求)、DBMS 内部特征 (存取方法、存储结构)。
    • 内容: 为关系模式选择存取方法；设计关系、索引等数据库文件的物理存储结构。

  • 关系模式存取方法选择:

    • B+ 树索引:
      • 对经常在查询条件、聚集函数参数、连接条件中出现的属性 (列或组合列) 建立索引。
      • 考虑是否唯一索引。索引过多会增加开销。
    • Hash 索引:
      • 属性主要出现在等值连接或等值比较选择中。
      • 关系大小可预知且不变，或 DBMS 提供动态 Hash。
    • 聚簇 (Clustering):
      • 将聚簇码 (属性 / 属性组) 上具有相同值的元组集中存放在连续物理块中。
      • 用途: 大大提高按聚簇码查询的效率。
      • 选择: 单个关系或常连接的多个关系 (预连接)。
      • 设计候选聚簇: 考虑连接操作、相等比较、高重复值属性。
      • 检查候选聚簇: 移除全表扫描、更新远多于连接、重复出现的关系。
      • 局限性: 只提高特定应用性能，建立维护开销大。适用于聚簇码访问是主要应用，尤其含 ORDER BY, GROUP BY 等。

  • 确定数据库的存储结构:

    • 数据存放位置:
      • 考虑因素: 硬件环境、应用需求 (存取时间、空间利用率、维护代价 - 常需权衡)。
      • 原则: 易变与稳定部分分开；经常存取与低频存取部分分开。
      • 例如: 大表分磁盘存放，日志与数据对象分磁盘。
    • 确定系统配置:
      • DBMS 提供的存储分配参数 (用户数、打开对象数、内存、缓冲区、块大小、装填因子、时间片、锁数等)。
      • 根据应用环境调整，初步设定后根据实际运行情况再调整。

  • 评价物理结构:

    • 定量估算各种方案的存储空间、存取时间、维护代价。
    • 权衡比较，选择较优方案。

7.6 数据库的实施和维护

  • 数据的载入和应用程序的调试:

    • 数据装载方法: 人工或计算机辅助。
    • 应用程序设计与数据设计并行，数据入库同时调试应用。

  • 数据库试运行:

    • 联合调试。主要工作:
      • 功能测试: 测试应用程序各项功能。
      • 性能测试: 测量系统性能指标，分析是否符合设计目标。不符则返回物理或逻辑设计调整。
    • 注意事项:
      • 数据的分期入库: 先小批量调试，合格后再大批量。
      • 数据库的转储和恢复: 试运行阶段系统不稳定，需做好备份恢复。

  • 数据库的运行和维护 (主要由 DBA 完成):

    • 数据库的转储和恢复: 定期备份数据库和日志文件，故障时恢复。
    • 数据库的安全性、完整性控制: 根据用户需求和环境变化，定义和修改权限及约束。
    • 数据库性能的监督、分析和改进: 利用监测工具获取参数，分析并调整以优化性能。
    • 数据库的重组织:
      • 原因: 记录增删改导致物理存储变坏，性能下降。
      • 目标: 提高性能。
      • 工作: 按原设计重排存储、回收垃圾、减少指针链。不改变逻辑和物理结构。
      • DBMS 通常提供相应工具。
    • 数据库的重构造:
      • 原因: 应用环境变化导致原有设计不满足新需求。
      • 工作: 调整数据库模式和内模式 (增删数据项 / 表，改类型 / 容量，增删索引等)。
      • 程度有限: 若变化太大，可能需重新设计整个系统。
